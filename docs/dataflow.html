AniQube 資料流程

一次 npm run sync 從 YouTube 抓到網站 JSON 的全部步驟，以及「改了規則要重跑什麼」。

打網路，花 YouTube 配額 純本機運算，免費、秒級 快取檔（存在 sync/cache/） 輸出，網站讀這些

流程

① 抓 YouTube（三個頻道）約 2,700 單位

run.mjs fetchChannel()

會員清單（UUMO）→ 上傳清單 → 播放清單 → 每個清單的影片編號 → 影片細節（標題、秒數、可否嵌入、地區限制、觀看數）。

這是唯一花配額的步驟，每天上限 10,000 單位。抓取不套任何過濾規則，用量只隨頻道內容增減，跟規則無關。
↓原樣存檔

② 原始資料快取raw.json

會員編號、上傳編號、播放清單、所有影片細節。一個字都不過濾。
npm run rebuild 從這裡開始，跳過 ①，不需金鑰、不花配額。
↓

③ 過濾與分季本機

run.mjs buildChannel() → lib.mjs classifyVideo / buildSeasons / dropCovered / buildStandalones

濾掉預告、直播、會員限定、台灣封鎖、長度不符；一個播放清單成為一季；丟掉被別季涵蓋的重複清單；只收劇場版／特別篇為單篇。

規則在 sources.json：titleDeny、memberMarkers、minSec、standaloneAllow⋯
↓

④ 對應到 AniList 編號本機

lib.mjs match / splitName + manual-matches.json + anime-offline-database（aod.json，24 小時快取）

清理標題 → 查名稱索引 → 同名多筆時用季數、年份挑一筆。人工對應表優先。對不上的歸入 unmatched，用猜的歸入 guessed。

↓

⑤ 向 AniList 取作品資料不花 YouTube 配額

run.mjs anilist()，每 50 部一次，約 15 次請求

題材、標籤、評分、人氣、簡介、封面、橫幅。成人類（Hentai）在這裡被丟掉。

↓

⑥ 組成資料並檢查本機

題材／標籤中文名來自 taxonomy.mjs；片庫縮水超過 30% 就中止、不覆蓋
↓

⑦ 輸出public/data/

index.json（所有季的卡片資料）、seasons/<id>.json（每季的集數與簡介）、report.json（未對應、猜的）→ 瀏覽器讀取，搜尋篩選全在本機

為什麼之前每次調整規則都要重跑

之前

抓取和過濾黏在同一個函式裡，抓完直接過濾，原始資料沒有存。所以不管改的是過濾、對應還是題材名稱，都只能從 ① 重來，每次約 2,700 單位。一天跑 3 次就接近 10,000 的上限。

現在

抓取（①）不做任何過濾，全部存成 raw.json；所有規則都在 ③ 之後才套用。改任何規則都只要 npm run rebuild，0 單位、約 1 秒。完整抓取只在每天排程時跑一次。第一次要先完整跑一次，才會產生這份快取。

改了什麼，要重跑到哪一步

你改的東西要重跑指令
過濾規則（收緊或放寬）：titleDeny、memberMarkers、長度門檻、standaloneAllow、重複季邏輯③ 起（0 單位）npm run rebuild
對應：manual-matches.json、match() 邏輯④ 起（0 單位）npm run rebuild
題材／標籤中文名：taxonomy.mjs⑤ 起（0 單位）npm run rebuild
前端畫面：src/不用 syncnpm run dev
新增頻道、想看頻道新上架的集① 起（完整）npm run sync（每天 GitHub Actions 也會跑）

規則收緊或放寬都一樣用 npm run rebuild。只有片源本身變了（新頻道、新上架）才需要完整抓取。
